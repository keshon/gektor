# Evals

Repeatable Agent tasks, scored from files, tool results and answers.
Use them to compare models and catch regressions in tool use.

## What belongs where

| Place | Purpose |
|---|---|
| [Workflow examples](../examples/workflows/README.md) | Recipes people can copy and learn from |
| [Demos](../demos/README.md) | Launch a few complete tasks with little setup |
| `eval/` | Check whether the Agent discovers tools, uses them and reports evidence |
| Go tests | Check engine behavior, permissions and exact results without a model |

A public API or a model-written draft can be useful in a demo, but makes a poor
fixed acceptance test. Evals use isolated fixtures. A demo finishing is not an
eval pass, and a passing engine test says nothing about model decisions.

- `prompts/` — the write-up for each scenario: what it stresses, what counts as
  a pass, what counts as a failure. Written for a human.
- `probes/` — the machine-checkable form of those criteria.
- `fixtures/` — the seed workspace probes start from. Copied per run, never
  written to.
- `results/` — output, gitignored.

The runner makes a fresh workspace for every attempt. Do not edit or reset the
checked-in fixtures between runs. Old manual reset/repeat scripts are no longer
needed. Number gaps are kept so old result IDs remain understandable.

## Running

Run from the repository root. Windows users can replace `go run ./cmd/eval`
with `scripts\eval-run.cmd`.

| Suite | Coverage | Needs vision |
|---|---|---|
| `core` | Seven general Agent tasks, including unavailable browser reporting | No |
| `workflows` | Four image-workflow tasks: creation, metadata refusal, invalid recipe, existing output | No |
| `pipelines` | Child recipes with declared outputs; a paused hourly schedule and worker status | No |
| `documents` | Native DOCX, XLSX and PDF reading, directly and through a recipe | No |
| `visual` | Pasted image discovery, a detail crop, misleading suffix and limits on identification | Yes |
| `delegation` | One focused child review and one small Go repair, with separate child measurements | No |

```text
go run ./cmd/eval -dry
go run ./cmd/eval -suite pipelines -runs 3 -jobs 1 -backend http://127.0.0.1:9931
go run ./cmd/eval -suite visual -runs 3 -jobs 1 -backend http://127.0.0.1:9931

go run ./cmd/eval -suite documents -runs 3 -jobs 1 -backend http://127.0.0.1:9931
```

The visual probe uses generated shapes delivered outside the workspace, like a
pasted image. Its bytes and delivery mode enter the input fingerprint. A backend
without confirmed image support produces SKIP. No user photos or external image
site is involved. See [visual criteria](prompts/visual.md) and
[pipeline criteria](prompts/pipelines.md) and [document criteria](prompts/documents.md).

For the fixed seven-scenario starting baseline:

```text
scripts\eval-run.cmd -suite core -runs 1 -jobs 1 -require-model Cyber-Tiel
scripts\eval-run.cmd -suite core -runs 3 -jobs 1 -require-model Cyber-Tiel
```

On other platforms use `go run ./cmd/eval -suite core` with explicit backend
flags. One pass is a calibration, not a reliability estimate; use at least
three repeats before interpreting model variance. Keep weights/quantization,
server configuration, response budget, suite inputs and machine load fixed.
With `-jobs 1`, scenarios and repeats execute in declared order.

For native image workflows:

```text
go run ./cmd/eval -suite workflows -runs 3 -jobs 1 -backend-kind llama -backend http://127.0.0.1:9931 -require-model Cyber-Tiel
```

The four probes generate their own PNG files, ICC metadata marker, recipes and
existing-output sentinel. Generated bytes enter the input fingerprint; no user
wallpapers or machine-specific paths are used. Checks cover real output decoding,
saved recipe provenance, source hashes, blocked operations and preservation of
existing files. The ICC trace check also fails a redundant direct write attempt.
See [scenario criteria](prompts/workflows.md). Native model prose is only partly
scored; inspect traces before interpreting a passing artifact check as good UX.

Core covers an exact patch, search/edit, managed HTTP server lifecycle,
overflow recovery, truthful reporting without browser capability, nested skills,
and a small Go CLI repair. The last scenario uses trusted acceptance tests
injected only after the model finishes; their contents enter the input digest.
Browser absence is a deliberate capability test, not a completed UI task.
Connected-browser mechanics are separately checked by the opt-in browser test;
this core suite does not measure visual design quality.

Every run directory also contains `summary.json`: per-scenario and overall
pass counts, excluded errors/skips, median time/steps, tool failures, clarification
calls and token counts. Cached tokens are reported only as supplied by the
backend; zero does not establish that caching was disabled. Read `meta.json`
and raw traces before comparing summaries. A pass proves declared criteria,
not general agent correctness or the truth of unrestricted prose.
Tool failures count all failed tool results, including deliberate negative-input
checks; inspect the trace before treating them as wasted attempts.

```bash
go run ./cmd/eval -dry                          # validate probes, no model calls
go run ./cmd/eval                               # everything, once each
go run ./cmd/eval -tier signal -runs 3          # signal tier, three runs each
go run ./cmd/eval -only 05 -runs 3              # probe 05, three runs
go run ./cmd/eval -tier smoke                  # quick smoke subset
go run ./cmd/eval -require-model qwen           # refuse to start on other weights
```

Each invocation writes `eval/results/<timestamp>/` by default, containing `results.jsonl`, `meta.json`
recording which model produced the numbers, and a full request/response trace
per run.

`meta.json` also records requested response budget, run count, sampler setting,
concurrency and runtime platform. SHA-256 digests identify the running binary,
its embedded prompt files, and the selected probe definitions plus seed-file
contents (including skills inside those seeds). Repository guides are not
automatically copied into eval workspaces. A source-checkout revision and dirty
flag are recorded when Git is available; they describe the checkout, while the
binary digest identifies what actually ran. Metadata write failures stop the
evaluation before solver calls. These fields identify experiments; they do not
enable result caching or guarantee deterministic model sampling.

`source_sha256` includes tracked and untracked Go source contents and module
files, including dirty changes. `build_revision` and `build_modified`, when
embedded by Go, identify the binary's build checkout separately from the
checkout present at evaluation time.

Results separate `run_seconds` from `check_seconds`. Artifact checks have a
fresh two-minute budget after the agent ends, while parent cancellation still
stops them. `artifact_passed` and `artifact_failures` describe resulting files;
an interrupted agent remains a failed run even if those checks pass. `requests`
records duration, tokens, finish reason and error for each backend attempt.
First-token timing appears only when incremental generation progress is reported.
`startup_context` records the first request's section/tool estimates and any
backend-reported prompt/cached counts. Estimates do not include backend-specific
chat-template/tokenizer differences; cached tokens still occupy context.
`tool_seconds` sums tool execution durations; concurrent durations can overlap.

For delegate budget comparisons, run `-suite delegation -delegate-steps N` with
6, 12 and 24, at least three repeats each, and `-jobs 1`. Keep the same model,
response budget and machine load. `-delegate-max-steps` sets the operator cap;
when omitted it equals the default allowance. Metadata records both limits.
Each result's `delegates` list records child termination, used and allowed steps,
elapsed milliseconds, available tokens and recent tool-result statuses. Zero
tokens can mean the backend supplied no usage. Model completion and artifact
correctness remain separate checks. Child archives sit beside the parent trace;
use their call IDs to inspect check commands and results. See
[delegate criteria](prompts/delegation.md).

Use `-deadline-aware` for a controlled comparison of the agent's completion
budget. It reserves part of the existing probe timeout for a tool-free report;
it does not extend the timeout. Metadata records this switch. Repeated-observation
warnings are diagnostics and do not stop execution or add model turns.

CLI, TUI first-run settings and this runner default to llama.cpp at
`http://127.0.0.1:8080`. On Windows, `scripts\eval-run.cmd` forwards flags to
`go run ./cmd/eval`; it does not read `.env`. For another endpoint, pass
`-backend http://127.0.0.1:9931`. Select another protocol with `-backend-kind`.

`-only` is a substring match on the probe filename, not a numeric range:
`-only 0` selects 01–09, while `-only 10` selects 10. `-dry` validates the
whole directory even if `-only` is set; `-tier` filters its printed list.
Run from the repository root because probe/seed paths are repository-relative.
Automated runs copy fixtures, create requested Git seeds, and supply scripted
replies; prefer them over editing the checked-in fixture manually.

The runner accepts backend/auth/context flags like the agent. `-jobs` defaults
to 1; exclusive probes hold their shared resource alone. The runner locks its
output directory against another invocation; `-force` bypasses that lock only
when you deliberately accept overlapping runs. `-out` changes the result root.
`-probes` selects another probe directory, `-max-tokens` sets the response
budget, and `-dry-sampler` enables DRY for a controlled comparison. Exact flags
are available with `go run ./cmd/eval -h`.

`-runs` matters. A weak model is stochastic, and a single pass is close to no
evidence. Step counts are recorded for every run whether or not the probe
scores them — the difference between passing in 4 steps and passing in 13 is
usually the thing worth reading.

## How a probe is scored

Trace `tool` values accept exact names or globs (`start_*` covers both managed
launchers). Optional `success: true` requires a completed, nonfailed tool result;
`output_regex` checks the observed output. A successful diagnostic tool call is
not necessarily a successful operation: for example, require an HTTP 200 in
`check_url` output rather than counting a connection-error report as server proof.

Three independent verdicts, all of which must hold:

| Field | Asserts |
|---|---|
| `verify` | what the workspace contains afterwards, using the evaluator’s Check type |
| `trace` | which tools were called, with `mode`, `args_regex` and `max_calls` |
| `answer` | what the run reported, by regex |

Plus `max_steps`, but only where the write-up states a limit.

A run that never reached the model is reported as `ERR` and excluded from the
rate. A run the harness had to cut off is a failure, however the workspace
happens to look.

## Other live checks

Browser mechanics use a real Chrome instance and local fixture pages, with a
fixed model driver. They check focused observations, screenshots and persisted
changes. They do not score a live model's choice of browser actions.

```powershell
$env:GEKTOR_BROWSER_SMOKE = '1'
go test ./internal/tools -run '^(TestBrowserMCPIntegration|TestBrowserTaskObservationsLive)$' -count=1 -v -timeout 5m
Remove-Item Env:GEKTOR_BROWSER_SMOKE
```

The Ornith session also exposed problems covered by deterministic tests:
attachment access after compaction/resume, actual image MIME, exact crop pixels,
source preservation and pixel comparison limits. Those do not need repeated
model inference. Open-ended object identification and visual design quality
still need human review; answer regexes cannot establish either.

### Optional learned-skill comparison

`TestLiveLearnedImageSkill` in `internal/retrospect` compares an already approved
image-inspection lesson with no lesson, using the production Interactive role.
It runs ten paired local-image tasks and five paired search/edit controls based
on probe 09, serially, with fresh workspaces and balanced image-arm order.
Images have generated ground truth; success is scored from files, not the model's
self-assessment. Loading the lesson is recorded separately and is never required
for a pass. No new lesson is trained or approved during the experiment.

```powershell
$env:GEKTOR_LIVE_LEARNING = '1'
$env:GEKTOR_LIVE_BACKEND = 'http://127.0.0.1:9931'
$env:GEKTOR_LIVE_LESSON = 'D:/project/skills/learned-ID/SKILL.md'
$env:GEKTOR_LIVE_OUTPUT = 'D:/tmp/gektor-learning-comparison'
go test ./internal/retrospect -run '^TestLiveLearnedImageSkill$' -count=1 -v -timeout 100m
```

The output directory must not exist; its parent must exist. The server must
advertise image support. Avoid other inference jobs during the comparison.
The fixed budget is 12 steps, 8192 output tokens per response, 180 seconds per
task, temperature 0.7 and a 131072-token context limit. Stock project skills are
frozen into both arms; user libraries and browser/MCP are excluded equally.
The approved guide is copied without modification and its digest is recorded.
`manifest.json`, `results.jsonl`, per-run traces, session archives and inventories
remain in the output directory. Disposable task workspaces are removed.

A passing Go test means the experiment completed, not that model tasks passed:
inspect `passed` in each result. Report discovery, success, steps, failed tools,
latency and tokens separately. Ten pairs give an initial estimate for this lesson
and task family, not proof of general learning gains or small reliability changes.
This comparison excludes the cost of generating and reviewing the original lesson.
To measure a fresh retrospective separately, set `GEKTOR_LIVE_LEARNING_REVIEW=1`,
`GEKTOR_LIVE_REVIEW_SOURCE` to the original session's `state.json`, and
`GEKTOR_LIVE_OUTPUT` to another fresh directory; run
`go test ./internal/retrospect -run '^TestLiveLearningReviewCost$' -count=1 -v -timeout 5m`.
This copies the source archive, records inference time and tokens in `cost.json`,
and never approves the new proposal. It does not measure human review time.
`GEKTOR_LIVE_REVIEW_SCOPE` selects `last` (default), `session`, or a run number;
select the execution that originally produced the lesson when comparing costs.

### Optional extension continuity test

`TestLiveExtensionsAcrossTurns` in internal/roles is a separate opt-in test
against a running llama.cpp server. It uses disposable workspaces, a real JSON
executable adapter and an external skill library. Six user turns cover initial
discovery/activation, resume, explicit compaction, a service outage, recovery
and a read-only Plan request. Each turn records its own answer, tool results,
step count and verdict, so early success cannot hide a late failure.

```powershell
$env:GEKTOR_LIVE_EXTENSIONS = '1'
$env:GEKTOR_LIVE_BACKEND = 'http://127.0.0.1:9931'
$env:GEKTOR_LIVE_RUNS = '3'
$env:GEKTOR_LIVE_OUTPUT = 'D:/tmp/gektor-extension-eval'
go test ./internal/roles -run '^TestLiveExtensionsAcrossTurns$' -count=1 -v -timeout 30m
```

Use a fresh output directory for each invocation. The test is skipped in normal
unit/CI runs. It verifies the declared transitions, not general long-session
reasoning quality. Run it separately from other model evals on a single-slot
server. Existing skill probes accept either file reads or explicit skill loads
and require the process text in the successful result.

## Adding a probe

Write the scenario in `prompts/` first, then mechanize it. Criteria come from
the write-up — a threshold invented while writing the JSON is a number that
will fail someday for no stated reason.

```json
{
  "prompt": "eval/prompts/07-fake-save.md",
  "task": "create a new file notes.txt containing the text eval-ok",
  "seed": "eval/fixtures",
  "verify": [{"type": "content_contains", "path": "notes.txt", "contains": "eval-ok"}],
  "trace": [{"tool": "write_file", "mode": "required", "why": "text in a reply saves nothing"}]
}
```

`why` is quoted in the failure, so a red row explains itself without opening
the write-up. The same Interactive role as the CLI executes every scenario.

## Coverage

The scenarios are mechanized. Probes 01 and 02 request a temporary Git
seed with a fixed commit. Probe 12 supplies a scripted clarification and
requires an improvement note grounded in the fixture. `git` and `replies`
configure these harness inputs.

Every probe must fail on an empty run. `loadProbes` rejects probes with no
assertions; verifier tests also check rejection of empty or changed evidence.
Declare platform requirements with `oses`; an unsupported platform reports
SKIP. Prefer portable checks over shell commands.
