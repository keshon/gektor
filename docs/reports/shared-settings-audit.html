One application, one settings workspace

Implemented flows, renderer previews and live acceptance steps

Source audit · 13 October 2026 · implementation completed 14 October

What is broken

  1. Model selection disappears in Agent. Settings offers inspection only; editChat returns immediately outside Chat except for Speech. This blocks the same task after a mode switch.
  2. Settings mixes configuration and execution. Plan/Act appears in both Agent and Settings. Execution policy belongs in Agent.
  3. Application settings are an isolated island. Conversation mode opens an Application-only workspace. It cannot lead naturally to Thinking, Generation, or Profiles.
  4. Profiles are framed as Chat presets. Agent inherits a chat-named profile, while the profile picker and save flow live in Chat settings. Mode and service configuration need distinct identities.
  5. Apply has inconsistent effects. Chat can preserve an active conversation while changing its model; application changes restart the TUI and services. The UI needs to describe the actual pending effect.
  6. Runtime failures expose technical logs instead of a recovery flow. Unsupported model architectures should produce an actionable message and a route back to Thinking.

Shared information architecture

Settings opens one workspace in both modes, remembering the last selected page.

  • Application: Chat / Agent, workspace, voice Off / Push-to-talk / Hands-free.
  • Thinking: Local / External, searchable model picker, model folders, connection test; runtime details under Advanced.
  • Generation: context window, response budget, sampling supported by the active backend. Show unsupported controls explicitly.
  • Speech: microphone, recognition, synthesis, reference voice, preview and capture controls.
  • Profiles: load a configuration preset, save a copy; mode remains visible and explicit.
  • Character and Prompts: available in Chat. Agent instructions and tool permissions need their own Agent page; character instructions must not silently replace coding policy.

Agent owns Plan / Act, permissions, run controls. Session owns new, browse, rename and delete. Voice owns immediate capture/playback controls and links to Speech settings.

Primary flows

Change model → Settings → Thinking → choose installed model → review context / runtime → Apply → keep session and draft → load on next request.

Switch mode → Settings → Application → Chat / Agent → choose workspace if needed → Apply → retain archive and carry compatible context → Agent starts in Plan.

Load preset → Settings → Profiles → preview changed values → Apply → retain session; disclose any incompatible context or service restart.

Apply footer states: Unsaved changes · model restarts on next request · session retained. Unchanged Apply is disabled. Failed application retains the draft and previous configuration wherever possible.

Implementation order and acceptance

  1. Extract the shared profile/settings controller from chatUI. Both modes use the same Thinking, Generation, Speech and Profiles pages.
  2. Wire Agent model changes through the application handoff while preserving history, draft, workspace and permissions. Never trigger a run from Apply.
  3. Unify menus and expose Application in the shared category list. Remove Plan/Act from Settings.
  4. Add model-load recovery messages and a shortcut to Thinking.

Accept only after testing: Agent model selection before its first turn and after a completed run; Chat ↔ Agent with an unsent draft; voice on/off; failed model load and recovery; external server selection; profile save/reload. Existing archives remain unchanged and no permission is granted by a settings change.

Evidence: internal/tui/header.go, settings.go, application.go, settings_workspace.go. Live terminal navigation was not tested in this audit.
